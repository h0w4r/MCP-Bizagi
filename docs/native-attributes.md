# Native extended attributes and embedded files

This is an **experimental source capability after 0.4.0-alpha.1**, not a claim of
complete Modeler automation or inclusion in the existing 0.4 release archive.
Build current source for these tools. Native integration is restricted to the
locally tested Modeler 4.3.0.008 adapter.

## Tools and durable workflow

| Tool | Purpose |
| --- | --- |
| `native_attributes_get` | Native definition XML, per-element value XML, source SHA-256 revision and embedded-file inventory |
| `native_attributes_apply` | Explicit definition upserts/deletions, complete per-element value replacements and embedded-byte transactions |
| `native_attachment_export` | Export one native-loaded embedded file or image to an operation artifact, independently checking bytes and SHA-256 |

Each tool returns an operation ID. Poll `operation_get`; a queued operation is
not a successful write. Changes require `expectedRevision` and produce a new
`artifact:<operation-id>:edited.bpm`, never overwrite the source, and must pass a
fresh-worker load plus whole-native-archive comparison before being completed.

The adapter uses installed native `ExtendedAttributesHolder<ElementType>`,
`ExtendedAttribute<ElementType>`, `ElementAttributeValues`, `TableRowValues`,
`AttachmentAttributeValue`, the persistence facade and native V5 persistence.
It does not patch a ZIP to pretend that a native save succeeded. The host reads
archive leaves only for independent comparison. No dialog, Office application,
mouse macro or foreground input is involved.

## Definitions

`NativeDocumentationPatch.Definitions` contains `NativeAttributeDefinition`
objects: `Operation` (`upsert` or `delete`), canonical native `Id`, and `Xml`.
An upsert is an explicit complete definition, not an arbitrary reflection path.
Deletion accepts no XML, requires an existing local definition and rejects
remaining references. Clear its values in a preceding verified operation first.

The native types are `Text`, `LongText`, `Number`, `Date`, `Image`, `Combo`,
`Radio`, `Check`, `FileEmbedded`, `FileLinked`, `Link`, and `Table`.
Their desktop meanings and differences are described in the
[official type reference](https://help.bizagi.com/platform/en/extended_attributes_type.htm).
Persistence acceptance alone does not establish every editor-specific constraint,
rich-text rendering behavior or visual compatibility.

Example definition XML, using IDs and `ElementType` from your native model:

```xml
<ExtendedAttribute Id="33333333-3333-4333-8333-333333333333"
                   Type="Text" ExportAsTable="false" Visible="false">
  <Name>Review notes</Name>
  <Description>Additional process documentation</Description>
  <Options />
  <TableColumns />
  <ElementTypes>
    <AttributeElementType Type="AbstractTask" />
  </ElementTypes>
</ExtendedAttribute>
```

Replace the example identity with your own unique GUID. Attribute applicability
uses **native element types**, not the XML BPMN tag or CLR class name. Retrieve
existing definitions before editing them; preserve their options, columns,
visibility, color and applicability intentionally. Root modification audit
fields are generated by native persistence rather than treated as user content.
Column metadata and all other unrequested content remain subject to comparison.

Native order positions are preserved when updating a definition; newly applicable
definitions are appended. Removed applicability and deleted definitions are
removed from the corresponding native order. Arbitrary order rearrangement and
global-catalog definitions are not yet advertised by these tools.

## Element values and table cells

`NativeDocumentationPatch.Values` contains `NativeAttributeValues` objects with
`DiagramId`, `ElementId`, and complete `ElementAttributeValues` XML. Supplying
`<Values />` explicitly clears that element's values. This is **not** a merge:
start from `native_attributes_get` and retain every value you wish to keep.

```xml
<ElementAttributeValues ElementId="22222222-2222-4222-8222-222222222222">
  <Values>
    <ExtendedAttributeValue Id="33333333-3333-4333-8333-333333333333" Type="Text">
      <Content>Reviewed — Ω</Content>
      <DisplayValue>Reviewed — Ω</DisplayValue>
      <TableValues />
    </ExtendedAttributeValue>
  </Values>
</ElementAttributeValues>
```

Table definitions contain native `ColumnAttribute` definitions in `TableColumns`;
table values contain `RowValues` in `TableValues`. Each cell uses its column's
identity and type. Unknown column references, mismatched types, duplicate values
within a row and rows on a non-table value are rejected. Native XML defaults must
match the durable readback; omitted content is not silently waived.

## Embedded files, images and linked references

`NativeDocumentationPatch.Attachments` contains `NativeAttachmentChange` objects:
`Operation`, `DiagramId`, `ElementId`, plain `FileName`, and `DataBase64` for an
upsert. The byte limits are **8 MiB per file**, **32 MiB per transaction**, and
1,000 combined patch items. Empty files are valid; deletion accepts no payload.
Windows device names, path separators, alternate streams and ambiguous trailing
characters are rejected independently of the host OS running public unit tests.

Embedded file/image values require the native attachment subtype:

```xml
<ExtendedAttributeValue xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
                        xsi:type="AttachmentAttributeValue"
                        Id="33333333-3333-4333-8333-333333333333" Type="FileEmbedded">
  <Content>attachment:Evidence.txt</Content>
  <DisplayValue>Evidence.txt</DisplayValue>
  <TableValues />
  <DisplayName>Evidence.txt</DisplayName>
</ExtendedAttributeValue>
```

The definition must have the same native type. `attachment:` is a server-side
reference notation, not a Bizagi URI scheme. Only embedded references are mapped
to the native scratch folder. Native persistence packages the actual bytes;
fresh-worker inspection checks their presence, length and SHA-256. An `.xml`
file attached by a user remains opaque bytes rather than being misclassified as
native metadata.

To remove a file, explicitly clear its value and delete its bytes in the same
transaction. Unrequested garbage collection of another file fails fidelity.
The acceptance circuit verifies deletion of a file while preserving a separate
image attachment. Replacing bytes without changing the reference is supported.

`native_attachment_export` takes `path`, `diagramId`, `elementId`, and `fileName`.
Its completed result includes `artifactPath`, the original file name, native
identity, verified byte count and hash. The physical export uses an opaque
`attachment.bin` name to avoid collisions with model artifacts; the original
name remains in `attachment.FileName`. It never executes or opens the payload.

**Linked files are references, not embedded bytes.** The tools do not open,
download or copy linked targets. A relative link is interpreted relative to the
model's location; moving a copy elsewhere can change its resolution. Choose
the intended location/reference explicitly. Native BPMN export excludes
extended attributes; it is not a backup format for this data.
[Official BPMN export limitations](https://help.bizagi.com/platform/en/exporting_to_bpmn.htm).

## Evidence and remaining boundaries

Run the actual stdio client against the installed engine:

```powershell
dotnet run --project tests/McpBizagi.Acceptance -c Release --no-build -- `
  D:/MCP-Bizagi --native --attributes-only
```

The circuit covers definition creation, scalar values, a two-row table, an
installed-renderer PNG, opaque embedded bytes, byte replacement, explicit removal,
definition rename/deletion, rich no-op save, an unrelated name edit, and real
failure/recovery. `documentation-acceptance.json` and the MCP transcript retain
private evidence. They may contain native audit identities: do not publish them
unredacted. Consult [validation](validation.md) for sanitized run identifiers.

Rich-text formatting, the complete numeric/selection validation corpus, nested
table/image combinations, custom artifacts, manual attribute order editing,
global catalogs, rich publication boundaries and independent Modeler visual
verification still require broader acceptance. No successful write proves those
capabilities, and none is silently promoted to full automation.
